- [x] FC-262 oMLX stopped reusing the system prompt between questions
  - Notes: found during FC-256 (2026-09-30). On the grounding eval every question showed 0 cached tokens, against 4,096 on 2026-09-20; first words median 2.40 s against ~0.7 s then. A direct probe (`scripts/probes/cache.ts`) shows the cache itself works — an identical repeat 0.31 s instead of 9.4 s — but a new question after the same prefix restored only 8,192 of 15,215 tokens, and oMLX's log says "0 intermediate snapshots": it keeps only the tail of each request. `~/.omlx/settings.json` changed 2026-09-30 12:07 and has `"gdn_snapshot_storage": "embedded"`. oMLX settings are the player's: measure and recommend, never edit.
  - Acceptance: the cause pinned to a setting or an oMLX version change, with evidence from oMLX's own logs and a before/after probe; a recommendation the player applies themselves; the latency report and grounding eval re-run once it's applied, with cached tokens back near the system prompt's size and the numbers in PLAN §5.
  - Done (2026-10-02). Not a setting: oMLX 0.7.0 (first seen in the 2026-09-26 log) widens Flash-Next's prefill step to 8,192 on this 64 GB+ machine and enlarges the cache block to match ("Enlarging paged cache block_size=256 to 8192 for ArraysCache hybrid model"), with no switch to turn it off; its hybrid layers resume only from a block boundary or a request's own end. Our stable prompt, padded for 2,048 blocks to 4,121 tokens, ended before the first boundary. So the fix was ours, not the player's: the server pads past the engine's block (`engines.ts`: 8,192 for oMLX, 2,048 for another local engine, `COMPANION_CACHE_BLOCK` overrides). Probe (`scripts/probes/block-8192.ts`): 2.04 s → 0.56 s server first token on never-seen questions, cached 0 → 8,192. Through the server: grounding 10/10, every question 8,192 cached, first token median 2.40 s → **0.68 s**. Nothing in oMLX was changed. PLAN §5 and CLAUDE.md updated.
